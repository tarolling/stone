# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

stone is a small Python-like language implemented in Rust (edition 2024, only dependency: `clap`, except for the opt-in `self-update` feature). The workspace also holds `lsp/`, the `stone-lsp` language server, which has its own dependencies, and `editors/vscode/`, a VS Code extension that runs it. One binary provides both a tree-walking interpreter and a compiler for x86-64 and arm64 Linux and arm64 macOS. Blocks open with `:` as in Python (e.g. `if x:`, `fn f(a: int, b: int) -> int:`), and `;` is not a token at all (`unexpected character ';'`); functions return with `ret`, and `continue` is `cont`. Every function parameter has a type, and a function that returns a value writes `-> T` (without it, it returns no value, and its call can only be a statement); nothing else is ever annotated. Enums are Rust's algebraic data types (`enum Shape:` with a variant per line, `Shape.Circle(1.0)`, `match s:` with `case Shape.Circle(r):`), and `option[T]` (`some(x)` or `none`) is the enum built in; `none` is only an option. Structs are Rust's structs, data only for now: `struct Point:` with a typed field per line (`x: float`), made with a named value for every field in any order (`Point(x=1.0, y=2.0)`), read as `p.x`, and changed in place as `p.x = v`, `ps[i].x += v`, or `p.items.append(v)`; like lists they are values. An `impl Point:` block, in the struct's own file, holds its functions: a method takes `self`, untyped, first and is called as `p.norm()`, and an associated function is called as `Point.origin()`; a method that changes `self` changes its receiver in place, as `append` does, with no keyword, and its call is a statement or the whole value of an assignment. Maps are `map[K, V]` with `int`, `str`, or `bool` keys, written `{"a": 1}` (`{}` empty), read as `m[k]` (failing with `key not found: 'k'`), set as `m[k] = v`, with `len` and `contains`, kept in insertion order, and values like lists. See `examples/basics.stn` for a sample program.

## Philosophy

`docs/philosophy.md` is the source of truth; read it before designing a feature. In short: Python's simplicity with Rust's memory safety, speed, and error reporting, achieved by moving all complexity into the compiler, and compiled programs that depend on no libc (raw syscalls on Linux, the thinnest system layer on macOS and Windows) and no gcc, since `stone build` assembles and links itself. If the compiler can infer something (types, ownership, laziness, copies), the language never asks the programmer to write it, with one exception: function signatures are written, for readable contracts and errors at the place a mistake is made, and everything inside them is inferred, as in Rust; prefer changing semantics so the fast, safe choice is always valid over adding a keyword. stone has value semantics: assignment, argument passing, and storing in a list behave as copies, implemented with copy on write and in-place updates of uniquely owned values, so a function changes its caller's list only by returning it (`xs = f(xs)`, which both backends turn into an in-place update by moving `xs` into the call, as they move any value at its last use). When goals conflict, rank safety, then programmer simplicity, then clear errors, then speed, then compiler simplicity. Keep the page's "Status" notes current as work lands.

## Architecture

The crate is a library (`src/lib.rs`) plus a thin CLI (`src/main.rs`, clap only). Pipelines are wired in `src/driver.rs`:

- **load** (`driver::load`, used by `run` and `build`): `project::link` (`Lexer` → `Parser` for the entry file and every module it uses, then linking) → `TypeChecker`, returning a `Checked` (the linked `Mod`, any warnings, which `run` and `build` print before going on, and the checker's `Methods`, which `run_module` gives the interpreter) and a `SourceMap` for rendering diagnostics from any file
- **run** (`driver::run_module`): load → `Interpreter`. `driver::interpret` does the same for a single source string with no other files
- **build** (`driver::compile_module`, given a `Target`): load → `Target::generator` (`X64Generator`, or `Arm64Generator` for the target's `Os`) → `compile` (check, scan pass lowers to IR, generate pass allocates registers and emits, then `codegen::link` writes the `.s` file, and `codegen::executable` encodes it with `asm::assemble` and links it with `elf::link` or `macho::link`)
- **repl** (`driver::repl`): `repl::run` on a `Limits::STACK_SIZE` thread with one `Interpreter` for the whole session. Each entry is checked through `driver::load` together with the text of every earlier kept statement (`Session`), minus any function the entry defines again, then only its statements run (`Interpreter::run_entry`, which echoes non-`none` expression values). An entry is read until `repl::needs_more` says it is complete (a `:` ending a line opens a block, closed by a blank line); prompts go to stderr only when stdin is a terminal A `Chunk` lists what it defines (an `impl` block each of its functions, as `S.get`), and an entry replaces every kept chunk that defines any of the same.
- **check** (`driver::check_program`): `project::link` → `TypeChecker`, returning every `Diagnostic` instead of running. `driver::analyze_linked` is the entry point for editor tooling

Key pieces:

- `src/span.rs`: `Pos` (1-based line and col, counted in chars), `FileId` (the entry file is `FileId(0)`), and half-open `Span`, which holds a `FileId`. Every token and AST node carries one. `Span::new` puts a span in the entry file, and `Lexer::with_file` lexes another file.
- `src/project.rs`: multi-file programs. The entry file's directory is the root, and `a/b.stn` is the module `a.b`; directories are only parts of names, so there are no barrel files. `use a.b` binds the module (called as `b.f()`), `use a.b.f` binds a `pub fn` of `a.b` (a module file wins over a function of the same path), and `as` renames. Library modules hold only `use`, `fn`, and `enum`, so importing runs nothing and cycles are fine, and their functions cannot see the entry file's names. `pub enum` is imported like a function (`use zoo.Animal`, `Target::Enum`, `public_enums`), and `Rewriter` renames enums to `<module>.<Name>` in signatures and variants (`type_expr`), in front of a variant (`name`, `qualified_enum` for `zoo.Animal.Fish`), and in patterns (`pattern`). `link` loads files through `Sources` (`FsSources`, or `MapSources` in tests), reports `use`/`pub` errors with the checker's wording, and merges every file into one `Mod` in which each library function is renamed to `<module>.<name>` and each use of it rewritten to that name, so the checker and both backends run unchanged (`fn.geometry.shapes.area` is a valid label). `link_in` picks another root, for editors. `pub struct` works as `pub enum` does: `public_types` lists a file's enums and structs together, `is_struct` tells `use geo.Point` to give `Target::Struct` rather than `Target::Enum` (both bind `Binding::Type`), and `module_call` rewrites `geo.Point(x=1)` to a call of the linked name `geo.Point`. `os`, `math`, `random`, and `time` are builtin modules with no file (`stdlib::MODULES`, `Loader::resolve_builtin_module`, `Target::BuiltinModule`): `use math`, `use math.sqrt`, and `use math as m` work anywhere, calls are rewritten to linked names such as `math.sqrt` like library functions, and a `math.stn` (or `os.stn`, ...) in the root is an error. The checker reports any `use` left in the module, which can only be a nested one. Tests in `src/project/tests.rs`. An `impl` block must name a struct of its own file (`own_structs`; an enum or an imported struct is an error), is renamed like the struct in a library, and its functions are rewritten as `fn`s are (`Rewriter::function`) but keep their names, since their linked name is the struct's plus theirs; `report_method_collisions` reports a module function with the same linked name as a method.
- `src/diagnostic.rs`: `Diagnostic` (severity, span, message) with `render` for the CLI, and `Diagnostics` for returning several as one error. Every stage's errors convert to it.
- `src/token.rs`: `Token`/`TokenType` and `RESERVED_KEYWORDS`. The lexer (`src/lexer.rs`) emits Python-style `Indent`/`Dedent`/`Newline` tokens, and `->` as `Arrow`, and reads string escapes (`\"`, `\'`, `\\`, `\n`, `\t`, `\r`, `\xhh` up to `\x7f`, never `\x00`, since compiled strings are null-terminated). `context::escape` writes other control characters into `.string` directives as three octal digits, which `asm::parse_string` reads.
- `src/ast.rs`: AST (`Mod`, `Stmt`, `Expr`, `Constant`, `ParserError`, `TypeExpr`, a type written in a signature, which `Arg::annotation` and `FunctionDef`'s `returns` hold, …), modeled on the ASDL in `docs/grammar/stone.asdl`. `ExprKind::Tuple` is a tuple of two or more values (`(1, "a")`, ctx `Load`) or, as an `Assign` or `For` target, names to unpack into (`q, r` or `a, (b, c)`, ctx `Store`), whose names `target_names` collects; `TypeExprKind::Tuple` is `tuple[int, str]`. `constant_int` reads an int literal, possibly negated. `Expr` and `Stmt` are structs of a `kind` (`ExprKind`/`StmtKind`, the ASDL variants) plus a `span`, so match on `&expr.kind`. A method call such as `xs.len()` is a `Call` whose `func` is an `Attribute`; attributes mean nothing outside a call. A slice `xs[a:b:c]` is a `Subscript` whose `slice` is an `ExprKind::Slice` (each bound optional), which appears nowhere else; `stdlib::slice_indices` turns its bounds into Python's `slice.indices` for both backends. An augmented assignment `target op= value` is its own `StmtKind::AugAssign`, not rewritten to `Assign`, because an element's indexes are evaluated once: indexes, then the old element (an index out of range fails before the value runs), then the value. The checker records the operation's type at the statement's span; the interpreter's `augmented` and `element` compute it, and `Lowerer::aug_assign` lowers a name target as the equivalent `Assign` (so `a += b` writes over `a` in place) and an element as a borrowed `ListLoad`, the operation (`Lowerer::binary` or `elementwise_tree`), then `store_element`. `StmtKind::EnumDef` holds `Variant`s (name and field `TypeExpr`s), and `StmtKind::Match` holds `MatchCase`s, each a `Pattern` (`PatternKind::Wildcard` for `_`, `Name` to bind, or `Variant` with a `path` such as `["Shape", "Circle"]`, `["some"]`, or `["none"]` and field patterns; `Pattern::names` lists what one binds) and a body. Any written type other than `int`/`float`/`bool`/`str`/`list`/`tuple` is `TypeExprKind::Named` (an enum, maybe dotted, or `option[T]`). Variant values need no new expression kind: `Shape.Circle(1.0)` is a `Call` of an `Attribute` and `Shape.Empty` an `Attribute`, which the checker, interpreter, and lowering recognize because the name before the dot is an enum. `StmtKind::StructDef` holds `Field`s (name and `TypeExpr`). `ExprKind::Call` has `keywords`, the named values (`Keyword`) after the positional ones, which only a struct takes; the checker reports them anywhere else. An `Attribute` outside a call is a struct's field, and as a target (ctx `Store`) a change. Parser tests build expected trees with `.into()` and compare them through `without_spans`. `StmtKind::ImplDef` holds an `impl` block's `FunctionDef`s (`parse_impl_def`, `parse_methods`, which hints at `pub fn`).
- `src/parser.rs`: hand-written recursive-descent PEG parser. Syntax errors come from the furthest token any rule failed at: `expect`, `expect_name`, `expect_block_start` (the `:` that opens a block, never quiet, though `Colon` elsewhere is), and `record_expected` note what was wanted there, and "quiet" expectations (operators, keywords, and other optional continuations) only show when nothing else was expected. A rule that recognizes a common mistake notes a `hint` at the token where it stopped, which replaces the message if parsing fails there: values separated by commas without parentheses (`x = 1, 2`, `ret a, b`; `parse_expressions` parses one expression and hints at a comma list), `()`, `(x,)`, `a, = t`, `tuple[int]`, `none` as a type, `Circle()`, and a literal as a pattern. `parse_enum_def` and `parse_match_stmt` read their own `NEWLINE INDENT ... DEDENT` blocks of variants and of `case pattern ':' block`s (`parse_pattern`); `case` is the one keyword besides `in` that is not a quiet expectation. `parse_struct_def` and `parse_fields` read a struct's `NAME ':' type` lines, `parse_args` reads `NAME '=' expression` as a keyword (`parse_kwarg`, looking ahead for `=`) and hints at a positional value after one, and `parse_target_with_star_atom` accepts `t_primary '.' NAME` as a target. `parse_tuple_or_group` parses `'(' expression` once and then decides, so nesting stays linear, and `parse_star_targets` takes names separated by commas, nested in parentheses through `parse_star_atom`. The struct, token helpers, and `parse()` entry are here; rules live in `src/parser/expressions.rs` and `src/parser/statements.rs` as `pub(super)` methods so siblings can call each other. Functions mirror rule names in `docs/grammar/stone.gram` (derived from CPython's grammar), e.g. `parse_t_primary`, `parse_star_targets`, `*_loop0` for repetition. Keep the `.gram`/`.asdl` docs in sync when changing syntax.
- `src/checker.rs`: `TypeChecker::analyze` infers types (`int`, `float`, `bool`, `str`, `list[T]`, tuples, enums and `option[T]` as `Type::Enum`/`Ty::Enum` with type arguments, monomorphic functions) by unification, taking each function's parameter and return types from its signature (`declare_function`, `Inference::written`; no `->` is `Type::Unit`, no value, which `infer` reports anywhere but an expression statement: `'f' returns no value`). The parser accepts a parameter without a type so editors keep working, and `finish` reports it, and a value returned from a function without `->`, suggesting the type inference found, resolves names Python-style (a function's params and assigned names are local, other names are globals or top-level functions, which are visible before their definition), and returns an `Analysis`: sorted diagnostics, the `Type` of every expression keyed by span, and `Symbol`s with every `Reference`. It only accepts what both backends run identically, e.g. conditions must be `bool` (`if 1 or 0:` is an error), arithmetic never mixes `int` and `float` (convert with `int()` or `float()`), even element by element, `==` cannot compare lists or maps, even inside a tuple, struct, or enum (`equalities`, which `finish` settles through `check_equality`; `uncomparable` finds the list or map and the struct field holding it, for the error), `range` only appears as a `for` iterable, functions must be top level, a method must be called (`xs.len`, without parentheses, is an error), and top-level code and functions must assign a variable on every path before reading it (`AssignmentCheck`). Since lists are values, a change (`xs[i] = v`, or a method that `stdlib::changes_receiver`, i.e. `append`) is a statement of its own, made to a variable or an element of one (`check_change`; `place` and `place_root` split such a target), and a function cannot change a global. `lost_change` warns when a function changes a parameter it never otherwise reads, and `collect_changed` lists the variables a body changes, for lowering. `pop` may also be the whole value of an assignment (`assigned_call`). Arithmetic works on numbers or, element by element, on `list[int]`/`list[float]` with a number broadcast to every element, so an operator becomes an `Arithmetic` that `solve_arithmetic` settles once its operands are known to be lists or numbers, and `finish` forces the rest (an unknown operand becomes a number); meanwhile `Bound`s on its unknown operands (`n` in `n * 2` is `int` or `list[int]`) make `unify` reject a wrong argument at the call, as before. `[x] * n` warns, since Python would repeat it. A tuple (`Type::Tuple`, `Ty::Tuple`, `Kind::Tuple`; `Type::leaves` flattens nested tuples and `field_leaves` finds a field's) is indexed only by a constant in range (`tuple_field`; `subscript_of` returns what it `Indexed`), only once its type is known, except that a constant index into a global a function reads before the code assigning it is checked is settled in `finish` (`DeferredIndex`). Tuples never change (`TUPLE_CHANGE`, also for a list inside one, through `indexed_tuples` in `check_change`), cannot be ordered, iterated, converted, or used in arithmetic or conditions, and unpack into names only, each once, as many as the tuple has values (`check_unpacking_names`, `unpack`, which records each nested pattern's type). A list element may hold at most `MAX_ELEMENT_VALUES` values (`check_element_width`, on list literals and written types). Enums: `declare_enums` registers every top-level `EnumDef` before functions (names first, so variants can hold any enum), with `SymbolKind::Enum` and `SymbolKind::Variant` symbols (a variant's `scope` is its enum, and `visible_at` hides it); `option` is built in (`OPTION`, tag 0 `none`, tag 1 `some`), and `variants`/`variant_display` give any enum type's variants and printed names, from `Analysis::enums` for the program's own. `infer_variant` checks `Shape.Circle(...)` and `Shape.Empty`, `none` is `option[fresh]`, `some` is a builtin, and `is_some`/`is_none`/`unwrap`/`unwrap_or` are option methods. `check_match` checks each `Pattern` against the subject (`check_pattern`, `variant_of_pattern`; names bind through `check_target`, and `collect_assigned` collects them, so they are ordinary variables), and `finish` runs `check_cases`, Maranget's usefulness check over `Space`s (`useful`, `missing`, `specialize`), for a missing pattern (an error naming it) and unreachable cases (a warning). Enums and options cannot be converted with `str`, iterated, or used as conditions; a match whose cases all exit `always_exits`. Structs: `declare_types` declares every enum's and struct's name before any variants or fields (`declare_struct_names`, `declare_fields`), so they can name each other, with `SymbolKind::Struct` and `SymbolKind::Field` symbols (a field's `scope` is its struct, and `visible_at` hides it), then reports a struct that `reaches` itself through fields and tuples alone (it may hold itself through a list or enum). A struct is `Type::Struct(name)`/`Ty::Struct`, nominal; `Analysis::structs` (`Structs`) holds each one's fields, which `Type::leaves` and `Type::struct_field` (a field's leaf range and type) need, since structs flatten like tuples (`Type::is_flat`), and `values`/`check_element_width` count their leaves. `infer_struct` checks `Point(x=..., y=...)` (every field once, named, no positional values) and records a reference on each keyword's name, `field_of` checks `p.x` (deferred like a tuple index for a global a function reads before its assignment, `DeferredField`), and `struct_display` is the printed name without the module. Places are steps (`Step::Index`/`Step::Field`): `place` splits `ps[i].x` into `ps`, the index `i`, and the field `x`, `place_spans` gives a span per step, and `check_change`, `collect_changed`, and `ParameterUse` treat a field target as a change to its root variable, so a function owns a struct parameter whose field it assigns. Methods: `declare_methods` declares each function of an `impl` block in `functions` under `<struct>.<name>` (`signature` gives a first untyped `self` the struct's type and reports `self` anywhere else), with a `SymbolKind::Method` symbol whose `scope` is the struct, and `struct_methods` records whether it has `self` and, from `find_changing_methods`, whether it changes `self` (a fixpoint over the bodies that types places in `self` from the fields' written types alone). `infer_associated` checks `Point.origin()` (`struct_named`), and `infer_struct_method` a method on a struct, before any builtin method of the same name, applying `append`'s rules (`check_change_of`) to one that changes `self`; a receiver of unknown type is settled in `finish` (`DeferredMethod`, after `DeferredField`s). Every resolved call goes in `Analysis::methods` (`Methods`, a `Method` per call span), which `changed_receiver`, `collect_changed`, and `lost_change` take so a changing method counts as a change.
- `src/interpreter.rs`: evaluates the AST directly over runtime `Value`s (`Value::Tuple` is an `Rc<[Value]>`, which `assign_target` unpacks after the whole value is evaluated; lists are `Rc<Vec>` values that a change copies first through `Rc::make_mut` if anything else shares them; `eval_place` evaluates a change's indexes and `place_list` walks to the list it changes, counting in `copies` each shared list a change copies, which tests check; after each statement it drops the list variables the statement used for the last time (`LastUses`, per function and for the program), and `note_top_call` lets a statement's call take its arguments from them first, so a list nothing else holds changes in place, though never a global in the REPL); `ControlFlow` carries break/continue/return, and a function sees only its own scope and the globals. An enum value is `Value::Enum(Rc<EnumValue>)` (its printed name, tag, and fields), made by `Interpreter::variant` from the `enums` table that `EnumDef`s fill before anything runs, and matched by `pattern_matches`, and compared by `Value::equals`, which fails with `stdlib::COMPARE_DEPTH` past `MAX_PRINT_DEPTH` nested enum values as compiled code does; `EnumValue`'s `Drop` empties uniquely held values into a worklist, so a long chain drops without recursion. `Value::write` prints values, stopping at enum values nested more than `stdlib::MAX_PRINT_DEPTH` deep (`print` writes what it has, then fails with `stdlib::PRINT_DEPTH`), and `Value::Unit` is what a call without a value gives. A struct value is `Value::Struct(Rc<StructValue>)`, its `StructDef` (printed name and field names) filled from `StructDef` statements before anything runs; changes walk `PlaceStep`s through `walk_place` (`place_value`, and `place_list` for a list), copying a shared struct with `Rc::make_mut` (only list copies count in `copies`), `read_place` reads an augmented target's old value, `take_field` moves a field such as `b.items` into a call that replaces it, and `drop_values` frees enum and struct values with one worklist. Arithmetic goes through `Interpreter::arithmetic`, which computes operations on two numbers at once and leaves those with a list operand as a `Lazy` tree that `elementwise` checks for equal lengths and then evaluates one index at a time, which defines the order of runtime errors for compiled code too. `Limits` bounds fuel (loop iterations plus calls), total evaluation depth, and active calls (`max_calls`, the language's `stdlib::MAX_CALL_DEPTH`), and `print` writes to an injectable writer, `input`/`eof` read an injectable `BufRead`, and `args` returns injected arguments (`driver::interpret_with_io`; `interpret_with` gives empty input and no arguments). It flushes the writer before reading, so prompts show first. The driver runs it on a thread with `Limits::STACK_SIZE` of stack so 1,000 nested calls fit. `with_methods` (and `run_entry`) take the checker's `Methods`; each `Function` keeps the table of the check that saw its body, since REPL entries move. `call_method_of_struct` calls a resolved method: an associated function or a method that does not change `self` like any call, and one that does by `eval_place`, the arguments, taking the receiver out of its place (a clone if it is a global the method may read, or in a session), `invoke(.., keep_self)`, which returns what the method left in `self`, and storing that back.
- Runtime errors must match between backends, and print like checker errors (`file:line:col: error: message`, the source line, and carets) under both. The interpreter turns an error into a `Diagnostic` at the innermost expression that raised it (`interpreter::located`, in `eval_expr` and `arithmetic`; a change's index points at its subscript, `checker::place_spans`), and compiled code prints the same text: lowering records the span of every instruction (`Block::spans`, `term_span`), and each backend's `fail_here` asks `Context::fail_at` for a stub that stores a site record (the location and excerpt `SourceMap::site` renders, in `.rodata`) in `stone.site` before jumping to `stone.fail`. A call to one of `context::FALLIBLE_ROUTINES` stores its site first, for the routine's own siteless `fail_label`s. `recursion is too deep` points at the call, so each call to a stone function checks `stone.call_depth` before calling, and the prologue only counts. Without sources (`AssemblyGenerator::set_sources`, which `driver::compile_module` calls), failures print only `error: message`. A message with `{}` holes (`stdlib::INDEX_RANGE`, `STRING_INDEX_RANGE`, `LENGTHS_DIFFER`) gets ints written into them: the interpreter through `stdlib::fill`, and compiled code by putting them in the backend's `FAIL_VALUES` registers, from `Terminator::Fail`'s values (`fail "...", v1, v2`) or, for the inline list index check, setup lines that a `Context::fail_at_after` stub runs first, then jumping to `stone.fail_detail`, which writes the pieces of text (`Failure::pieces`) and the ints in turn without allocating. The interpreter's error message is what compiled code prints after `error: ` (e.g. `division by zero`, `integer overflow in division`, `recursion is too deep (more than 1000 nested calls)`, `'x' is used before it is assigned`, `list index out of range (index 5, length 2)`, `cannot convert float to int (nan or out of range)`), with exit status 1. Floats follow IEEE 754 except that dividing by 0.0 is `division by zero`, as in Python. Golden programs check them with `.err` files.
- Every stage must return an error, never panic, on bad input: `LexError` for bad literals, a `Diagnostic` from `Parser::parse`, `parser::MAX_DEPTH` for nesting, `Limits` in the interpreter, and `Err(String)` from codegen (`AssemblyGenerator::assemble` generates assembly text) and from the assembler and linker.
- `src/codegen.rs`: `AssemblyGenerator` trait (`compile`/`assemble`/`scan`/`generate`/`emit`/`target`), `Architecture` (`X64`/`Arm64`, the processor: `host`, and `generator` for Linux), `Os` (`Linux`/`MacOs`), `Level` (the processor features a target may assume, `v1`-`v4` on x86-64 and `v8`-`v9.5` on arm64; codegen ignores it for now), `Target` (an architecture, a `Level`, and an `Os`, named `<arch>[<level>]-<os>` with no vendor since programs use no libc: `X64_LINUX`, `ARM64_LINUX`, `ARM64_MACOS`, `ALL`, `host`, `generator`, `Display` as the canonical name such as `x86_64-linux` or `x86_64v3-linux`, and `FromStr` for `--target` names: a processor `x86_64`/`x64`/`aarch64`/`arm64` with an optional level, then optionally `-linux` or `-macos` (none means Linux), plus Rust's names such as `aarch64-apple-darwin` and `x86_64-unknown-linux-musl`; x86-64 macOS is the error `INTEL_MACOS`). Release archives use the same names for the machine the stone binary runs on, plus `x86_64-macos`), `executable`, which assembles and links in memory for a target, and `link`, which writes `<output>.s` and the executable beside `<output>` before renaming it over, so a running copy keeps working (macOS also kills a signed binary rewritten in place).
- `src/codegen/device.rs`: `Device`, a GPU named as its vendor does (`gfx1100`/`gfx90a` for amdgcn, `sm_90`/`sm_90a` for NVIDIA). GPUs are never part of a `Target`: a build will take one target plus any number of devices (`--gpu`, not added until a device backend exists).
- `src/codegen/asm.rs`: the built-in assembler. `assemble(text, arch)` parses the GNU as text both backends emit (labels, comments, `.text`/`.data`/`.bss`/`.section .rodata`, `.globl`, `.p2align`, `.balign`, `.zero`, `.quad`, `.string`; anything else is an error naming the line) and returns an `Object`: the bytes of `.text`, `.rodata`, and `.data`, the size of `.bss`, every label as a `Symbol`, and `Fixup`s (`FixupKind`) for addresses only the linker knows. An `Encoder` per target turns one instruction into `Encoded::Fixed` bytes or, on x64, an `Encoded::Branch` that starts short (2 bytes) and grows to rel32 until nothing grows, as GNU as relaxes jumps. `src/codegen/asm/x64.rs` (Intel syntax operands: registers by width, `QWORD PTR [base + index * scale + disp]`, `[rip + label]`, immediates including sums such as `8 + 4095`) and `src/codegen/asm/arm64.rs` encode exactly the instructions the backends emit, choosing GNU as's encoding where there are several (store-form `89` for `mov reg, reg`, `83` for small immediates, `movz`/`movn`/`orr` for `mov #imm`, `ldur` for unscaled offsets, `sub` for `add #-n`), so `tests/assembler.rs` can compare bytes exactly. A backend change that emits a new instruction form needs the encoder to learn it: get the bytes from GNU as (or `aarch64-linux-gnu-as`), add the line to the encoder's table test, then implement it.
- `src/codegen/elf.rs`: the built-in linker. `layout` places `.text` on the first 64-byte boundary after the ELF and program headers at `BASE` (`0x400000`), so loops sit in their cache lines as they would under GNU ld (a 16-byte start made `collatz` 20% slower), then `.rodata` and `.data` plus `.bss` each on a new page (`page_size`: 4 KiB on x64, 64 KiB on arm64) at the same offset within the page as in the file, and `link` resolves every fixup with `asm::apply_fixup` (shared with the Mach-O linker; an undefined symbol is the linker's error, not the assembler's) and writes an `ET_EXEC` with `PT_LOAD` segments (R+X, R, RW), a non-executable `PT_GNU_STACK`, section headers, and a `.symtab` of every label except `.L` ones (functions sized to the next symbol), entering at `_start`.
- `src/codegen/macho.rs`: the built-in Mach-O linker for arm64 macOS. `link(object, identifier)` writes a PIE `MH_EXECUTE` at `BASE` (`0x1_0000_0000`) with 16 KiB pages: `__PAGEZERO`, `__TEXT` (headers, `__text` on a 64-byte boundary, `__stubs`, `__const` from `.rodata`), `__DATA` (`__got`, `__data`, `__bss`), and `__LINKEDIT` (chained fixups, an export trie of `__mh_execute_header`, the symbol and indirect symbol tables, strings, then the signature), each at the same file offset as in memory except `__LINKEDIT`, which follows `__bss`. It loads `/usr/lib/dyld` and `/usr/lib/libSystem.B.dylib`, enters at `_start` through `LC_MAIN`, and requires macOS 12 (`LC_BUILD_VERSION`) for chained fixups. Each `bl` to a name in `SYSTEM_FUNCTIONS` (undefined in the object) resolves to a stub that jumps through a GOT slot holding a `DYLD_CHAINED_PTR_64_OFFSET` bind; nothing else holds an absolute address, so nothing is rebased. The `LC_UUID` is a hash of the contents, so builds are reproducible, and the file ends with an ad hoc, linker-signed code signature (SHA-256 of each 4 KiB page) because arm64 macOS runs only signed code. Tests in `src/codegen/macho/tests.rs` parse the output back.
- `src/codegen/sha256.rs`: SHA-256 for the Mach-O signature and UUID, so the crate keeps `clap` as its only dependency.
- `src/codegen/context.rs`: `Context`, the bookkeeping both backends share and hold as `ctx`: `check` (runs the checker) and `lower` (lowers to IR and notes the `Callee::Runtime` labels called, which `uses` answers), `new_label`, `intern_string`, `fail_label` and `fail_at` (a runtime error without or with a site), `set_sources`, `site_label`/`sites`, `print_routine`/`list_printers`, `needs_strings`/`needs_lists`/`needs_print`, plus `global_label`, `function_label`, and `immortal_string`.
- `src/codegen/ir.rs`: a small IR between the AST and assembly. A `Function` is blocks (in layout order) of `Inst`s over vregs, each ending in a `Terminator`; it is not SSA, so each stone local is one vreg for the whole function. `Display` prints a readable dump (`v1 = add v0, 1`, `br_lt v1, v0 -> b2, b3`), which tests compare and `STONE_DEBUG` prints. `Inst::Call` writes several `dsts` and `Terminator::Return` returns several values when a stone function returns a tuple (`v2, v3 = call divide(v0, v1)`, `ret v0, v1`), and `Inst::defs` lists what an instruction writes. `Retain` and `Release` (`retain v1`, `release_str v1`, `release_enum v1`) adjust a string's, list's, or enum value's reference count (`RcKind`, whose `codes` writes the 2-bit kinds of slots), and `ListStore` can return the element it replaces (`v3 = list_store v0, 1, v2`). `ListUnique` (`v0 = list_unique v0`) gives a list nothing else refers to before it changes, copying it if its count is above 1. `Terminator::Fail` (`fail "math domain error"`) stops the program with a runtime error, which each backend emits as a jump to a `fail_at` stub, and `FloatSqrt` is `sqrtsd` or `fsqrt`. `ListSet` is an unchecked store into an uncounted list, `ListData` loads a list's element pointer, and `Packed` (`v9 = packed v5, v3, fadd(fmul([v6], v2), [v7])`) runs a `Kernel` over pairs of elements with SIMD, writing the position where it stopped. `EnumTag` (`v1 = enum_tag v0`), `FieldGet` (`v2 = field_get v0, 1`), and `FieldInit` read an enum value's tag and slots, and `VariantStatic` (`v3 = variant 0`) is the static, immortal value of a variant without values, `stone.variant_<tag>`, which every enum shares by tag (`context::variant_statics`). A `Function` with `helper` is one lowering made, named by its label and called through `Callee::Helper`, which neither counts toward nor checks the call depth, and records the caller's site for its siteless `Fail`s.
- `src/codegen/ir/lower.rs`: `lower` turns a checked AST into a `Program` (every function, then `main`, plus the global names), resolving names like the checker (`checker::collect_assigned`). Tuples are never stored as one value: each value of a tuple variable `t` is a variable of its own, `t.0`, `t.1`, ... across nested tuples (`ir::leaf_name`, `ir::variable_of`, `Lowerer::leaf_names`), a local or a global (`g.t.0`, of which only the first is checked before a function reads it), so counting, moves, and releases work per value, while liveness stays keyed by stone names. `expr_flat` lowers any expression to its values (one, or one per value of a tuple), `tuple_field` picks `t[k]`'s, `user_call` passes a tuple argument as its values and receives a tuple result as several `dsts`, `assign_tuple` copies local values first so `a, b = (b, a)` swaps, `ret (s, s)` gives a local's own reference only once, and `print_flat` prints a tuple, and a list holding one (`print_elements`), a value at a time, with strings quoted. An element of a list of tuples is `width` slots read with `ListGet` and written with `ListSet` at `position * width + field` after an IR bounds check against the element count (`element_values`, `store_values`, `load_slots`); `pairs[i][0]` reads only its slot. Evaluation is left to right, so runtime errors happen in the interpreter's order. `x = <expr>` writes `x`'s vreg directly, unless `x` is counted. `if`/`while` tests go through `Lowerer::cond`, so comparisons, `and`, `or`, and `not` become `CmpBranch`/`Branch` terminators instead of materialized bools. A `for` loop counts with hidden vregs that the body cannot assign, and copies a variable bound or list first. It also places every `Retain` and `Release` (see "Memory" below), which needs each variable's type, so it takes the checker's `symbols` as well as `types`. A change evaluates its value, the indexes (`place_indexes`), and any arguments, then `unique_place` makes each list from the variable down unique with `ListUnique`, writing it back to the local, the global (only in `main`), or the parent slot, before the store or `stone.list_append`. A function owns the parameters it assigns or changes (`owned_params`), and `give_references` gives each such argument a reference before the call: a temporary's, a retained one, or, for a variable in `movable` (the variables the statement uses for the last time, `Lowerer::last_uses`, from `last_use::live_after`, plus an assigned target), the variable's own, which moves it in so the callee sees a count of 1. `take_from` moves a variable the same way into `ys = xs` or `rows.append(row)` at its last use. A moved variable that its statement does not assign again is left null (`clear_moved`), so releasing it later does nothing. A global moves only into a function that cannot read it, directly or through its calls (`last_use::global_reads`). Enums: `Lowerer::variant` makes a value with `stone.enum_new(tag, kinds, slots)` and `FieldInit`s each value of its fields (taken like a list literal's elements), or `VariantStatic` for one without values (and `none`), and `option_value` lowers `unwrap` (a `Fail` on tag 0) and `unwrap_or`. `match_stmt` evaluates the subject once (through a copy if it is a variable, since a case may assign it), holds a temporary subject in `held` so `ret`, `break`, and `cont` release it (`release_held`), then per case runs `pattern_test` (`EnumTag` and `CmpBranch` down the variants the pattern names) and `pattern_bindings`, retaining every bound value before assigning any. Printing an enum, or a list or tuple holding one (`holds_enum`), calls a helper per enum type, `stone.print_enum.<type>` (`Helper::Print`, `Helper::label`, `enum_printer`), which `lower` makes after every function until none is left asked for (`Lowerer::helper` asks), passing `print_depth` on and failing past `MAX_PRINT_DEPTH`. Structs lower like tuples: each struct variable is leaf variables (`leaf_names`, gated by `is_flat`), `construct` evaluates a struct's keyword values in written order and gives its leaves in field order, and `struct_field` reads a field's leaves (only its slots, for a list element). A change through a field goes through `locate`, which walks a place's steps to a `Location` (a variable's leaves, or slots of a list made unique on the way, each index checked against the element count), then `store_location` or, for `p.x += v` and `ps[i].x += v`, `aug_assign_place`; `unique_place` uses it for any place with a field, and a field assigned the result of a call is movable, so `p.items = f(p.items)` moves the list in. Structs print through a helper per struct type, `stone.print_struct.<name>`, taking the leaves and the depth, since a struct can hold a list of itself; struct values count toward `MAX_PRINT_DEPTH` in both backends. `==` and `!=` on tuples, structs, and enum values (`is_compound`) compare their leaves in turn, stopping at the first that differs (`equal_branch`, `equal_leaves`: `CmpBranch`, `stone.str_eq` for strings, and for an enum value a helper per enum type, `stone.eq_enum.<type>` (`Helper::Equal`, `enum_comparer`), which compares tags and then the variant's slots, passing `compare_depth` on and failing past `MAX_PRINT_DEPTH` with `stdlib::COMPARE_DEPTH`); `compare` writes 1 or 0, and `cond` branches on a single one directly, releasing temporaries on both ways out. `lower` takes the whole `Analysis`. Functions of `impl` blocks lower as functions named `<struct>.<name>`; a method that owns `self` (`returns_self`, since it changes it) returns its values after its result from every `leave`. `struct_call` lowers a resolved call: `user_call` for an associated function or, with the receiver first, a method that borrows `self`, and `changing_call` for one that changes it (`place_indexes`, the arguments through `give_references` from parameter 1, `locate`, then the receiver's values moved into the call, or retained if it is a global the method reads, and `store_location` of the returned values).
- Maps: the lexer's `LBrace`/`RBrace`, `ExprKind::Dict { keys, values }` (`parse_dict`), and `TypeExprKind::Map`. The checker's `Type::Map`/`Ty::Map` requires `MAP_KEYS` of the key through a `Constraint`, indexes a map in `subscript_of` (`Indexed::Map`, recording `indexed_maps`, and deferring an index into a global a function reads before its assignment through `DeferredIndex::index_ty`), and allows only `name[k] = v` as a change (`MAP_CHANGE` for `m[k] += v`, `m[k].append(x)`, or `p.m[k] = v`); `check_entry_width` bounds an entry at `MAX_ELEMENT_VALUES`. The interpreter's `Value::Map(Rc<MapValue>)` keeps entries in a `Vec` with a `HashMap<MapKey, usize>` of positions. Compiled, a map is a list object (`RcKind::List`) whose elements are entries, the key then the value's leaves (`Lowerer::element_kinds`), plus a hash index at `[p + 40]`, a slot every list header now has (48 bytes, 0 unless a map), which `free_list` frees and `list_copy` leaves 0 so a copy rebuilds it on first use. `builtins::map_runtime` (both backends, `context::MAP_ROUTINES`) has `stone.map_find` (first slot of a key's entry or -1) and `stone.map_add` (appends an entry, retaining a string key, growing the open-addressing index at half load), and `stone.map_missing_str` (in `parse_runtime`, a `FALLIBLE_ROUTINES` entry) fails through `stone.fail_quoted`. Lowering: `map_values` (reads, failing per key type), `map_store`/`map_put` (sets), the `Dict` literal, `contains`, and `print_entries` for printing. `stone.fail_detail1` takes a message with one hole, `stone.fail_detail` two.
- Arithmetic on lists: `Lowerer::elementwise` lowers a list-typed `BinOp`/`UnaryOp` tree (`fused` evaluates its other operands once, left to right, into a `Fused` tree), checks the lengths (`fail_unless`), takes the result from `stone.list_reuse` when an operand is in `movable` (its last use, or the assigned variable) so `a = a * 2.0 + b` writes in place, else `stone.list_new`, and loops with `ListGet`, the ordinary `Binary`/`FloatBinary`/`Neg`/`FloatNeg`, and `ListSet`. When `Fused::packable` (int `+ -` and negation, float `+ - * /` and negation) and small enough, a `Packed` instruction does whole pairs first and the scalar loop starts at its `done`. The backends expand `Packed` in registers no vreg uses: SSE2 in `xmm3`-`xmm15` (with `rax`/`rcx`/`rdx`) and NEON in `v16`-`v31`; a float division stops before a pair with a zero divisor so the scalar loop reports it at the interpreter's element, and FMA is never used. `pop` and `insert` check their index in IR (`list_position`), then call `stone.list_pop`/`stone.list_insert`; slices call `stone.list_slice`; all of these, `stone.list_extend`, and `stone.list_reuse` are `context::LIST_ROUTINES`, emitted by each backend's `builtins::list_methods` only when called.
- `src/last_use.rs`: liveness over the AST, shared by both backends: `global_reads` (a `GlobalReads` of the globals each function, including each function of an `impl` block, may read, through its calls too; a call `x.m()` counts as a call of every method named `m`), `live_after` (the variables code after each statement may read, keyed by statement span, iterating loops to a fixed point; nothing is live after `ret` but the `exit` set, `kept_at_exit`, which keeps a method's `self` to the end, and `break`/`cont` see where they jump), and `last_uses` (what each statement mentions that is dead after it).
- `src/codegen/ir/liveness.rs`: `analyze` computes live-in/live-out sets, then one interval per vreg (no holes). Each block gets a start position, then each instruction an even position where it reads and the odd one after where it writes. Intervals carry a spill weight (`10^loop_depth` per access) and whether they cross a call.
- `src/codegen/regalloc.rs`: target-independent `linear_scan` (Poletto-Sarkar, spilling the lighter interval) with `Hint`s for preferred registers (`hints` computes them from a function and its argument registers), and `parallel_moves`, which orders simultaneous moves and breaks cycles through a temporary.
- Returning a tuple: the first values come back in `RESULT_REGS` (x64 `rax`, `rdx`, `rcx`, never allocated; arm64 `x0`-`x7`) and the rest in an area the caller reserves just above the arguments it passes on the stack, which the callee writes at `[rbp + 16 + 8 * (stack params + j - 3)]` or `[x29, #16 + 8 * (stack params + j - 8)]` (`Frame::stack_params`; arm64's `outgoing` covers both). Only stone functions return several values.
- `src/codegen/x64.rs`: `X64Generator`, emitting GNU-as Intel syntax (`.intel_syntax noprefix`). `assemble` runs the checker first and lowers with its types, e.g. to pick a `print` routine per argument. Top-level statements always go in a synthesized `main`, which `_start` (`builtins::start_runtime`) calls with `argc`, `argv`, and `envp` as C would, then makes the `exit_group` syscall with its status. Globals live in `.bss` as `g.<name>`, and user functions are `fn.<name>`, so they cannot collide with runtime labels. String literals are interned and emitted in `.data` with an immortal reference count (`builtins::immortal_string`). Runtime errors jump to a `fail_at(message, span)` stub that records its site and calls `stone.fail`.
- `src/codegen/x64/emit.rs`: instruction selection from allocated IR. Vregs that cross a call get callee-saved `rbx`/`r12`-`r15` (saved in the prologue only if used); others may also use `rsi`, `rdi`, `r8`-`r11`. `rax`, `rcx`, `rdx`, and `xmm0`-`xmm2` are never allocated and serve as scratch, for `idiv`, spilled operands, and wide immediates. `hints` asks for arguments to be computed in their argument registers, parameters to stay where they arrive, and copies and two-address results to share a register. The first six arguments go in registers via `parallel_moves`; arguments past the sixth are pushed, first deepest, and the callee reads them from `[rbp + 16 + ...]`. Each function counts itself in `stone.call_depth`, which each call checks against `MAX_CALL_DEPTH` first, and each global has a `g.<name>.set` flag that `StoreGlobal` sets and that functions check before reading a global, since only top-level reads are checked statically. Floats travel as their bits in general registers and spill slots like every other value, and only move into `xmm` registers for SSE arithmetic, `ucomisd` comparisons, and conversions. Division checks for zero and `MIN / -1` before `idiv`, except that an immediate divisor other than 0 and -1 skips the checks, and a power of two becomes shifts (`divide_by_constant`). `%` shares those checks but gives 0 for a divisor of -1. `**` is an inline square-and-multiply loop (`power_loop`) that matches `stdlib::int_pow` and `stdlib::float_pow` operation for operation, and float `%` uses x87 `fprem`, so neither calls libc. List indexing is inline (`list_slot`): it counts negative indexes from the end, checks the result against the list header's length, and jumps to a `fail_at` stub when out of range. `Retain` is an inline `inc`, and `Release` an inline `dec` that calls `stone.free_str` or `stone.free_list` only when the count reaches 0. Those routines preserve every allocatable register, so neither instruction counts as a call for register allocation.
- `src/codegen/arm64.rs` and `src/codegen/arm64/emit.rs`: `Arm64Generator`, emitting GNU-as for AArch64 Linux from the same allocated IR, with the same labels, runtime failures, and `.bss` globals as x64. Arguments go in `x0`-`x7` and past the eighth at the bottom of the caller's frame (`[x29, #16 + 8k]` in the callee). Vregs that cross a call get `x19`-`x28`; others may also use `x0`-`x7` and `x12`-`x15`. `x8`-`x11`, `x16`, `x17`, and `d0`-`d2` are scratch, and `x18` is never used. `sp` stays 16-byte aligned at every instruction, so `push_frame`/`pop_frame` save registers in pairs and a frame reserves its spill slots and outgoing arguments once, addressing them from `sp`. Immediate forms of `add`/`sub`/`cmp` read register 31 as `sp`, so their first operand comes from `base`, never `xzr`. Behavior that differs from x86 is checked explicitly: `sdiv` never traps (zero and `MIN / -1` are tested first), `fcvtzs` saturates (the float is range-checked first), and float `%` calls `stone.fmod` (`arm64/floats.rs`), an exact remainder on the floats' bits, as musl's `fmod` computes it, that preserves every allocatable register. Float comparisons use `fcmp` with `mi`/`ls`/`gt`/`ge`/`eq`/`ne`, which are false on nan except `ne`. `src/codegen/arm64/builtins.rs` and `src/codegen/arm64/floats.rs` port every routine of `x64/builtins.rs` and `x64/floats.rs` under the same label and contract; the free routines take the object in `x9`. Every call into the system goes through `builtins::system_call` with a `Sys`: on Linux `mov x8, #n` and `svc #0`, and on macOS a `bl` to a shim `stone.sys_<name>` (`system_shims`, emitted for the calls the text makes) that saves `x1`-`x17` around the `libSystem` function, so only `x0` changes, as with `svc`. libSystem reports failure as -1, which the Linux checks for -4095 through -1 catch (the `getcwd` shim turns null into -1). The rest of the macOS runtime differs only where the systems do: `_start` is called by dyld as C calls `main`, `MAP_ANON` is `0x1002`, there is no `mremap` (large blocks move to a new mapping), `CLOCK_MONOTONIC` is 6, `os.platform` is `"macos"`, and `os.hostname`/`os.cpu_count` read `sysctl` (`kern.hostname`, `hw.activecpu`) as macOS's `gethostname` and `sysconf` do.
- Memory: compiled strings, lists, and enum values are reference counted (the interpreter's `Rc` values need nothing more, the checker's occurs check rules out cycles, and enum values never change). An enum value (`builtins::enum_runtime`, emitted when `Context::needs_enums`) is an object with its tag at `[p]`, the 2-bit kinds of its slots at `[p + 8]`, and its slots from `[p + 16]` (`ir::FIELDS_OFFSET`); `stone.free_enum` queues dead values on `stone.free_pending`, linked through their tags, and frees the queue in a loop guarded by `stone.freeing`, releasing strings and lists directly, so freeing never recurses through enum values, and `free_list` hands kind-3 elements to it. `stone.free_list` does the same for lists: a dead list joins `stone.lists_pending`, linked through its capacity slot, and the outermost call frees the queue in a loop guarded by `stone.freeing_lists`, so a struct holding a list of itself a million levels deep frees in constant stack. Every object `p` has its count at `[p - 8]`, and `stone.alloc` (`builtins::memory_runtime`) allocates one with a count of 1. Memory comes from the runtime's own allocator (`builtins::allocator`: `stone.mem_alloc`, `stone.mem_free`, `stone.mem_realloc`, which clobber only scratch registers), not libc: blocks of a power of two from 32 bytes to 64 KiB, with the exponent in an 8-byte header, are kept on a free list per size and cut from 1 MiB regions mapped with `mmap`, and larger blocks get a mapping of their own, grown with `mremap`. The constants are in `context.rs` (`SMALLEST_CLASS`, `LARGEST_CLASS`, `HEAP_REGION`). Strings stay null-terminated `char*`, and a string also holds its length in bytes at `[p - 16]`, so `stone.str_len` reads it rather than scanning (`stone.cstr_len` scans a C string, such as an argument, or a pointer into a string). Every string is made by `stone.str_new` (length, then count, then bytes and terminator), and `immortal_string` writes the same header for literals. A list is a 40-byte header `{len, cap, data, kinds, width}`: `len` and `cap` count 8-byte slots, each element is `width` slots (1, or one per value of a tuple, stored side by side), and `kinds` says, two bits per value of an element, whether it is counted (0 no, 1 strings, 2 lists, 3 enum values) so `stone.free_list` can release them; `stdlib::MAX_ELEMENT_VALUES` (32) bounds the width. `stone.list_new` makes a list of width 1 and `stone.list_new_wide` any other; `free_list`, `list_copy`, `list_extend`, and `list_slice` handle wider elements (the last three through `stone.retain_slots`), while appending, inserting, and popping an element of a list of tuples are `width` calls to the slot routines at the slot where it starts (`Lowerer::add_element`, `pop_element`). `lower.rs` keeps counts exact: variables and list slots each own a reference, expressions are borrowed (variables, globals, literals) or owned temporaries (call results, list elements, which are retained when read) that whatever uses them releases or moves into storage, parameters are borrowed unless the function assigns or changes them, in which case the caller gives them a reference, `ret` releases locals and the lists of enclosing `for` loops, and the end of `main` releases every global. A row in `a[i][k]` is borrowed rather than retained when the index makes no calls (`Lowerer::list_operand`). Before a change, `ListUnique` is an inline count check that calls `stone.list_copy` (in `list_runtime`; it preserves every allocatable register, so it is not a call either) only when the count is above 1, and the copy retains counted elements and drops the original's count by one. `stone.live` counts allocated objects, and `stone.leak_check`, called at the end of `main`, exits with `error: N objects were never freed` when `STONE_LEAK_CHECK` is set.
- Builtins: `BUILTINS` in `src/stdlib.rs` lists function names shared by both backends (`print`, `range`, `int`, `float`, `str`, `input`, `eof`, `args`, `some`), and `BUILTIN_DOCS` documents each for hover and the LSP's builtins reference. `METHODS` (`len`, `append`, `pop`, `insert`, `extend`, `strip`, `split`, `join`, `find`, `startswith`, `endswith`, the option methods `is_some`, `is_none`, `unwrap`, `unwrap_or`, and the map methods `contains` and `get`) and `METHOD_DOCS` do the same for builtin methods, which are called on a value (`xs.append(1)`, `s.len()`) and are not reserved names. `src/codegen/x64/builtins.rs` (and its port, `src/codegen/arm64/builtins.rs`) emits the hand-written runtime via `&mut dyn AssemblyGenerator`: `stone.print_*` routines (emitted if the program prints), the float runtime in `src/codegen/x64/floats.rs` (`stone.format_float`, shared by `stone.print_float` and `str`'s `stone.str_float`, takes the shortest digit count the way Rust's Dragon `format_shortest` does, then rounds the exact value half to even to that many digits, matching `stdlib::format_float`, which prints floats like Python's `repr`; `stone.decimal_to_float`, behind `float(str)`, multiplies or divides by an exact power of ten for up to 15 digits and 22 places, and otherwise divides two bignums exactly; both work on a small bignum library of 64-bit limbs in `.bss`, `bignum_runtime`), and the string and list runtimes (emitted if the program uses those types). Other routines are emitted only if the lowered IR calls them (`Context::uses`, over `Callee::Runtime` labels): `io_runtime` (`input` and `eof` over a 64 KiB buffer that the `read` syscall fills, `STDIN_BUFFER`), `args_runtime` (from `stone.argc`/`stone.argv`, which `main` saves on entry), `env_runtime` (`stone.getenv`, which walks the `stone.envp` that `main` saves, for `os.env` and the leak check), `parse_runtime` (`int(str)` with an overflow-checked accumulator, `float(str)` checking the grammar then calling `stone.decimal_to_float`, both mirroring `stdlib::parse_int`/`parse_float` and failing with a message built at runtime through `stone.fail_quoted`), `conversion_runtime`, and `string_methods` (the `context::STRING_METHOD_ROUTINES`: `strip`/`split`, mirroring `stdlib::strip`/`split_whitespace`/`split`; `stone.str_at` and `stone.str_slice_of` behind `s[i]` and `s[a:b:c]`, mirroring `stdlib::str_at`/`str_slice`, which index bytes and fail with `stdlib::CUT_CHARACTER` rather than cut a character outside ASCII, `stone.str_at` returning an entry of a table of 128 immortal one-byte strings; `stone.str_cmp` behind `<` on strings, which compares its -1, 0, or 1 with 0; `stone.str_char`, which a `for` loop over a string calls for the character at each position, stepping by its length; `join`, `find`, `startswith`, and `endswith`). A string inside a printed list prints as `stdlib::repr_in_list` writes it, like Python's `repr`, through `stone.print_str_quoted`. Whitespace is the ASCII set C's `isspace` uses (`stdlib::is_space`). Compiled programs call no libc: on Linux the runtime makes syscalls itself, and on macOS it calls only libSystem's syscall wrappers through `system_call` shims, which run on the 16-byte aligned stack arm64 always keeps; on x64 the stack needs no realigning, since generated code does not keep it aligned. `input` and `args` copy their text into counted strings. The builtin modules' functions are builtins too: `stdlib::MODULES` lists each `BuiltinModule` (its name, doc, and `DOCS` by linked name, such as `os.env`, from `src/stdlib/os.rs`, `math.rs`, `random.rs`, and `time.rs`, which also hold the functions the interpreter calls), and `stdlib::is_builtin` and `stdlib::module_function` accept them. `math` lowers to plain IR in `Lowerer::math` (compares, branches, and loops, with `Terminator::Fail` for its errors, and `FloatSqrt`), matching `stdlib::math` to the bit. The others lower to the runtime call `context::MODULE_ROUTINES` names (`stone.os_env`, `stone.time_sleep`, ...), except `random.randint` and `random.choice`, which check their arguments in IR and then call `stone.random_below`, and `os.env`, whose `stone.os_env` gives 0 for a variable that is not set. Builtins that may find nothing (`find`, `pop()` without an index, `get`, `os.env`) return an option, which `Lowerer::option_if` builds: `some` of the values on one branch (`new_variant`), the static `none`, retained, on the other. `random_runtime` keeps xoshiro256** state in `.bss` and draws exactly what `stdlib::random::Rng` draws, so seeded programs agree, seeding from `getrandom` (macOS `getentropy`) on first use otherwise; `time_runtime` makes `clock_gettime` and `nanosleep` calls. The `os` routines are emitted by `os_runtime` in both backends (`src/stdlib/os.rs` holds the only `unsafe` code, for libc's `gethostname` and `sysconf`) from the syscalls behind the libc calls the interpreter makes (`uname` for the host name, `/sys/devices/system/cpu/online` for the processor count, as glibc reads it; `sysctl` on macOS). An `os` routine that differs by system branches on `gen.target().os`. `os.exit` makes the interpreter return the error `interpreter::Exit`, which `driver::run_module`, `driver::repl`, and `main` turn into the exit status without printing anything, and compiled code makes the `exit_group` syscall, skipping the leak check. Adding a builtin means updating `BUILTINS` and `BUILTIN_DOCS`, its type rule in `Inference::infer_builtin`, the interpreter's `Interpreter::call`, and its lowering in `Lowerer::call` (plus an IR instruction and its emission in both backends if it is not a runtime call), plus a program in `tests/programs/`. A function of a builtin module follows the same steps with that module's `DOCS` (a new module also goes in `stdlib::MODULES`), plus either IR lowering or a `MODULE_ROUTINES` entry and a routine in each backend's runtime for the module. Its golden programs cannot be named after a builtin module, so `tests/programs/math_module.stn`, not `math.stn`. A method follows the same steps with `METHODS`, `METHOD_DOCS`, `Inference::infer_method`, `Interpreter::call_method`, and `Lowerer::method`, and both backends evaluate the receiver before the arguments. A method that changes its receiver is also listed in `stdlib::changes_receiver`, and runs through the interpreter's `place_list` and the lowering's `unique_place` instead, evaluating the receiver's indexes, then the arguments, then making the change.

Language server (`lsp/`, crate `stone-lsp`, depends on `lsp-server`, `lsp-types`, `serde_json`):

- `src/lib.rs`: `run(connection)` does the initialize handshake (preferring UTF-8 positions, falling back to UTF-16), keeps open documents with full-text sync, and dispatches requests through `Server::answer`. On every open/change/close it reanalyzes every open document, reading files through `Workspace` (open documents' text over the disk), and publishes each one's diagnostics, the changed document first.
- `src/features.rs`: one pure function per request (`diagnostics`, `hover`, `definition`, `references`, `prepare_rename`, `rename`, `document_symbols`, `completion`) over a `Document`, which holds the text, the `stone::driver::analyze_linked` result of the whole program it belongs to (`Document::in_program`: the nearest `main.stn` at or above it, or the file alone if that program does not use it), its `FileId`, the `SourceMap`, the program's imports, and a `LineIndex`. Spans in other files become locations through `Document::location`, and a library function's symbol is named `<module>.<name>`, which `Document::local_name` shortens. An enum hovers with its variants and outlines with them as children, a variant hovers as `Shape.Circle(float)`, and completion after an enum's name and a `.` offers its variants (`enum_variants`). A struct hovers with its fields and outlines with them as children, a field hovers as `Point.x: float` and renames everywhere, including `x=` in a construction, and completion after a variable holding a struct and a `.` offers its fields (`struct_fields`). Builtins have no stone source, so `run` writes `stdlib::builtins_reference()` (comment-only, documenting each builtin from `stdlib::BUILTIN_DOCS`) to `<temp>/stone-lsp-<version>/builtins.stn`, and `definition` of a builtin jumps to its line there (`Builtins`). Add a feature here with unit tests in `src/features/tests.rs`, then wire it into `Server::handle_request` and `capabilities`. A method or associated function hovers as `fn Point.shift(self, dx: float)` (`function_signature`), outlines under its struct after the fields (`struct_methods`, `function_outline`), and completion offers a struct value's methods with `self` (`has_self`) after its fields, and a struct's associated functions after its name and a `.`.
- `src/line_index.rs`: converts stone's 1-based char positions to LSP's 0-based UTF-16 or UTF-8 positions.
- `src/uri.rs`: converts between `file://` URIs and paths.
- Tests: unit tests for features and positions, `tests/server.rs` over an in-memory connection, and `tests/stdio.rs` against the real binary.
- `driver::analyze_linked` recovers from syntax errors statement by statement, in blocks too (`Parser::parse_recovering`, `parse_statements`), so features keep working around a typo, and it hides type errors until the syntax and `use` errors are fixed.

The logo is `docs/_static/logo.svg` (the S in Black Ops One, `#f1c232`), used by the docs and README. The VS Code extension can only package its own directory, so it keeps a copy as `editors/vscode/images/stone.svg` (the `.stn` file icon) and a 256x256 render as `editors/vscode/icon.png` (the Marketplace icon, which must be a PNG).

## Style

These apply to code, comments, docs, and commit messages.

- Never use em dashes.
- Never use emojis.
- Always use American English (e.g. "initialize", "color", "behavior").
- Doc comments (`///`, `//!`) are written in full sentences, and should include examples wherever practical:

  ```rust
  /// Rounds a frame size up to the 16-byte stack alignment required by the System V ABI.
  ///
  /// For example, `align16(20)` returns `32` and `align16(32)` returns `32`.
  fn align16(size: i32) -> i32 {
  ```

- Inline comments (`//`) start lowercase and are almost never full sentences, e.g. `// globals live in main's frame`, not `// Globals live in main's frame.`

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:

- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
