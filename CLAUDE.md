# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

stone is a small Python-like language implemented in Rust (edition 2024, only dependency: `clap`, except for the opt-in `self-update` feature). The workspace also holds `lsp/`, the `stone-lsp` language server, which has its own dependencies, and `editors/vscode/`, a VS Code extension that runs it. One binary provides both a tree-walking interpreter and a compiler for x86-64 and arm64 Linux. Syntax is designed to minimize Shift-key use: blocks open with `;` instead of `:` (e.g. `if x;`, `def f(a, b);`), functions return with `ret`, `continue` is `cont`. See `random.st` for a sample program.

## Commands

- Build: `cargo build`
- Test: `cargo test`. CI also runs `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings`
- Single test: `cargo test <name>` (e.g. `cargo test simple_functions`). Unit tests live in `#[cfg(test)]` modules in `src/lexer.rs`, `src/parser/tests.rs`, `src/checker/tests.rs`, `src/project/tests.rs`, `src/codegen/ir/lower/tests.rs`, `src/codegen/ir/liveness.rs`, `src/codegen/regalloc.rs`, `src/codegen.rs`, `src/codegen/x64.rs`, `src/codegen/arm64.rs`, `src/stdlib/os.rs`, `src/driver.rs`, `src/repl.rs`, and `src/update.rs` (which needs `--features self-update`). `tests/cli.rs` runs the binary to check error output and exit codes
- Golden-output tests: `tests/programs.rs` runs every `.st` in `examples/`, `tests/programs/`, and `docs/examples/` through both `stone run` and `stone build`, comparing stdout with the sibling `.out` file. A program that should fail at runtime also has a `.err` file holding text its stderr must contain. A sibling `.in` file becomes the program's stdin (otherwise it is empty), a `.args` file holds its command-line arguments, one per line, and a `.env` file holds `NAME=value` lines that every backend adds to its environment (for `os.env`). A subdirectory of one of those directories is a program of several files, run from its `main.st`, with `main.out` (and any `.err`, `.in`, `.args`, `.env`) next to it, as in `tests/programs/modules/`. Both backends must agree on everything the checker accepts, so `SKIPS` should stay empty. `stone build` targets the host, and a third pass (`build-aarch64` on x86-64, `build-x86_64` on arm64) cross-builds every program with `--target` and runs it under qemu-user when the cross gcc and `qemu-aarch64`/`qemu-x86_64` are on PATH, skipping with a note otherwise; qemu finds the target's libc through `QEMU_LD_PREFIX` (default `/usr/aarch64-linux-gnu`). CI's x86-64 job installs `gcc-aarch64-linux-gnu qemu-user`, and a `ubuntu-24.04-arm` job runs everything natively Built binaries run with `STONE_LEAK_CHECK=1`, so a program that ends with any string or list still allocated fails (see "Memory" below). Add a program plus its `.out` to cover new behavior
- Fuzzing: the `fuzz/` crate (cargo-fuzz, nightly) has crash targets `lex`, `parse`, `interpret`, `codegen`, and `structured`, plus `differential`, which compares `stone run` with `stone build` on generated programs. Run one with `cargo +nightly fuzz run parse -- -dict=fuzz/stone.dict`. `cargo test --manifest-path fuzz/Cargo.toml` checks the program generator on stable, including that generated programs pass the checker and that 150 of them print the same under both backends and free everything (needs gcc). `STONE_FUZZ_TARGET=aarch64` makes that check (and `differential`) build for aarch64 and run under qemu, like the cross golden pass. Turn each crash into a regression test, as a unit test or a `tests/programs/` program
- Benchmarks: `cargo run --release --manifest-path bench/Cargo.toml -- [--runs 5] [--filter fib]` times each program in `bench/programs/` under `stone build`, `gcc -O2`, `gcc -O0`, and `python3`, after checking all four print its `.out` file, and prints a Markdown table (needs gcc and python3). Each benchmark is a `.st`, `.c`, `.py`, and `.out` with the same stem. `cargo test --manifest-path bench/Cargo.toml` checks the runner and that every benchmark passes the checker. See `bench/README.md`
- Docs: `docs/` is a Sphinx site (Furo theme, Markdown pages via MyST). Build it with `pip install -r docs/requirements.txt` then `sphinx-build -W -b html docs docs/_build/html`. `.github/workflows/docs.yml` builds it on PRs and publishes it to GitHub Pages on pushes to `main`. Tutorial programs are `docs/examples/*.st` with `.out` files, shown via `literalinclude` and run as golden tests. `tests/docs.rs` fails until `docs/reference/builtins.md` has every `BUILTIN_DOCS` signature and `docs/reference/syntax.md` every keyword. `docs/_ext/stone_lexer.py` highlights stone code and lists the keywords and builtins too
- Interpret a file: `cargo run -- run examples/basics.st` (or `cargo run -- examples/basics.st`). `default-run` picks the `stone` binary, since the workspace also builds `stone-lsp`
- Compile a file: `cargo run -- build examples/basics.st [-o build/out] [--target x86_64|aarch64]` writes `<output>.s`, then invokes `gcc -g -no-pie ... -lm` to produce `<output>` (requires gcc on PATH; the default `build/out` is relative to the working directory). The target defaults to the host (`Architecture::host`), and another needs its cross gcc (`aarch64-linux-gnu-gcc` or `x86_64-linux-gnu-gcc`, `Architecture::linker`)
- Format: `cargo fmt`
- Lint: `cargo clippy --all-targets`
- Check a file without running it: `cargo run -- check examples/basics.st`. Errors print as `file:line:col: error: message` with the source line and a caret, and the exit status is 1
- Interactive session: `cargo run` with no file runs the REPL (`src/repl.rs`), and `printf 'x = 1\nx + 1\n' | cargo run` drives it without prompts
- Releases: `sh scripts/bump-version.sh <stone|vscode> <major|minor|patch|X.Y.Z>` bumps the version everywhere it is recorded (`vscode` sets the extension and `stone-lsp` to one version) and prints the commit and tag commands, and `sh scripts/test-bump-version.sh` tests it. Pushing a `v<digit>*` tag (`v[0-9]*`, so `vscode-v*` tags do not match) that matches `version` in `Cargo.toml` runs `.github/workflows/release.yml`, which builds `stone-<target>.tar.gz` plus a `.sha256` for x86-64 and arm64 Linux (musl) and macOS and publishes them as a GitHub release. `install.sh` (POSIX sh) downloads the archive for the current machine into `~/.local/bin` and verifies its checksum. `sh scripts/test-install.sh` (after `cargo build`) tests it against a local `file://` release via `STONE_DOWNLOAD_URL`, and CI runs both test scripts plus `shellcheck scripts/*.sh`
- Self-update: `stone self-update [--check] [--version <tag>]` replaces the binary with a GitHub release. It lives in `src/update.rs` behind the `self-update` cargo feature (the `self_update` crate with `ureq` and rustls), which only release builds enable, so default builds, CI's main test run, and fuzzing never pull in an HTTP stack. Without the feature the subcommand explains how to upgrade instead. It picks `stone-<target>.tar.gz` by exact name (`pick_asset`), checks it against the release's `.sha256` asset and GitHub's per-asset digest, and runs the new `--version` before swapping it in. CI also runs clippy and the unit tests with the feature on
- Language server: `cargo test -p stone-lsp` runs its tests, and `cargo install --path lsp` installs `stone-lsp`. See `editors/vscode/DEVELOPMENT.md` to try it in VS Code and to release it. The extension's `npm test` (in `editors/vscode`) tests `server.js`, which picks the server: the `stone.server.path` setting, else a bundled `server/stone-lsp`, else `stone-lsp` on PATH. Pushing a `vscode-v*` tag matching `editors/vscode/package.json`'s version runs `.github/workflows/vscode.yml`, which packages a `.vsix` per platform bundling `stone-lsp` plus a universal one and publishes them to the VS Code Marketplace and Open VSX (the Marketplace through a Microsoft Entra ID app registration via `azure/login` OIDC and `vsce publish --azure-credential`, since global Azure DevOps PATs retire December 1, 2026; Open VSX through the `OVSX_PAT` secret)

The `debug!` macro (defined in `src/lib.rs`) prints token dumps and parser traces to stderr only in debug builds with `STONE_DEBUG` set (e.g. `STONE_DEBUG=1 cargo run -- run file.st`), and never under `cargo fuzz`.

## Workflow

- Practice TDD. Write the test first, run it and confirm it fails for the expected reason, then write the implementation that makes it pass.
- After every change, run `cargo fmt` and `cargo clippy`, and address what clippy reports.

## Architecture

The crate is a library (`src/lib.rs`) plus a thin CLI (`src/main.rs`, clap only). Pipelines are wired in `src/driver.rs`:

- **load** (`driver::load`, used by `run` and `build`): `project::link` (`Lexer` → `Parser` for the entry file and every module it uses, then linking) → `TypeChecker`, returning the linked `Mod` and a `SourceMap` for rendering diagnostics from any file
- **run** (`driver::run_module`): load → `Interpreter`. `driver::interpret` does the same for a single source string with no other files
- **build** (`driver::compile_module`, given an `Architecture`): load → `Architecture::generator` (`X64Generator` or `Arm64Generator`) → `compile` (check, scan pass lowers to IR, generate pass allocates registers and emits, then `codegen::link` runs gcc)
- **repl** (`driver::repl`): `repl::run` on a `Limits::STACK_SIZE` thread with one `Interpreter` for the whole session. Each entry is checked through `driver::load` together with the text of every earlier kept statement (`Session`), minus any function the entry defines again, then only its statements run (`Interpreter::run_entry`, which echoes non-`none` expression values). An entry is read until `repl::needs_more` says it is complete (a `;` ending a line opens a block, closed by a blank line); prompts go to stderr only when stdin is a terminal
- **check** (`driver::check_program`): `project::link` → `TypeChecker`, returning every `Diagnostic` instead of running. `driver::analyze_linked` is the entry point for editor tooling

Key pieces:

- `src/span.rs`: `Pos` (1-based line and col, counted in chars), `FileId` (the entry file is `FileId(0)`), and half-open `Span`, which holds a `FileId`. Every token and AST node carries one. `Span::new` puts a span in the entry file, and `Lexer::with_file` lexes another file.
- `src/project.rs`: multi-file programs. The entry file's directory is the root, and `a/b.st` is the module `a.b`; directories are only parts of names, so there are no barrel files. `use a.b` binds the module (called as `b.f()`), `use a.b.f` binds a `pub def` of `a.b` (a module file wins over a function of the same path), and `as` renames. Library modules hold only `use` and `def`, so importing runs nothing and cycles are fine, and their functions cannot see the entry file's names. `link` loads files through `Sources` (`FsSources`, or `MapSources` in tests), reports `use`/`pub` errors with the checker's wording, and merges every file into one `Mod` in which each library function is renamed to `<module>.<name>` and each use of it rewritten to that name, so the checker and both backends run unchanged (`fn.geometry.shapes.area` is a valid label). `link_in` picks another root, for editors. `os` is a builtin module with no file (`Loader::resolve_os`, `Target::BuiltinModule`): `use os`, `use os.env`, and `use os as system` work anywhere, calls are rewritten to linked names such as `os.env` like library functions, and an `os.st` in the root is an error. The checker reports any `use` left in the module, which can only be a nested one. Tests in `src/project/tests.rs`.
- `src/diagnostic.rs`: `Diagnostic` (severity, span, message) with `render` for the CLI, and `Diagnostics` for returning several as one error. Every stage's errors convert to it.
- `src/token.rs`: `Token`/`TokenType` and `RESERVED_KEYWORDS`. The lexer (`src/lexer.rs`) emits Python-style `Indent`/`Dedent`/`Newline` tokens.
- `src/ast.rs`: AST (`Mod`, `Stmt`, `Expr`, `Constant`, `ParserError`, the `Type` annotation enum, …), modeled on the ASDL in `docs/grammar/stone.asdl`. `Expr` and `Stmt` are structs of a `kind` (`ExprKind`/`StmtKind`, the ASDL variants) plus a `span`, so match on `&expr.kind`. A method call such as `xs.len()` is a `Call` whose `func` is an `Attribute`; attributes mean nothing outside a call. Parser tests build expected trees with `.into()` and compare them through `without_spans`.
- `src/parser.rs`: hand-written recursive-descent PEG parser. Syntax errors come from the furthest token any rule failed at: `expect`, `expect_name`, and `record_expected` note what was wanted there, and "quiet" expectations (operators, keywords, and other optional continuations) only show when nothing else was expected. The struct, token helpers, and `parse()` entry are here; rules live in `src/parser/expressions.rs` and `src/parser/statements.rs` as `pub(super)` methods so siblings can call each other. Functions mirror rule names in `docs/grammar/stone.gram` (derived from CPython's grammar), e.g. `parse_t_primary`, `parse_star_targets`, `*_loop0` for repetition. Keep the `.gram`/`.asdl` docs in sync when changing syntax.
- `src/checker.rs`: `TypeChecker::analyze` infers types (`int`, `float`, `bool`, `str`, `none`, `list[T]`, monomorphic functions) by unification, resolves names Python-style (a function's params and assigned names are local, other names are globals or top-level functions, which are visible before their definition), and returns an `Analysis`: sorted diagnostics, the `Type` of every expression keyed by span, and `Symbol`s with every `Reference`. It only accepts what both backends run identically, e.g. conditions must be `int` or `bool`, arithmetic never mixes `int` and `float` (convert with `int()` or `float()`), `==` cannot compare lists, `range` only appears as a `for` iterable, functions must be top level, a method must be called (`xs.len`, without parentheses, is an error), and top-level code and functions must assign a variable on every path before reading it (`AssignmentCheck`).
- `src/interpreter.rs`: evaluates the AST directly over runtime `Value`s (lists are shared `Rc<RefCell<Vec>>`); `ControlFlow` carries break/continue/return, and a function sees only its own scope and the globals. `Limits` bounds fuel (loop iterations plus calls), total evaluation depth, and active calls (`max_calls`, the language's `stdlib::MAX_CALL_DEPTH`), and `print` writes to an injectable writer, `input`/`eof` read an injectable `BufRead`, and `args` returns injected arguments (`driver::interpret_with_io`; `interpret_with` gives empty input and no arguments). It flushes the writer before reading, so prompts show first. The driver runs it on a thread with `Limits::STACK_SIZE` of stack so 1,000 nested calls fit.
- Runtime errors must match between backends: the interpreter's error message is what compiled code prints after `error: ` (e.g. `division by zero`, `integer overflow in division`, `recursion is too deep (more than 1000 nested calls)`, `'x' is used before it is assigned`, `list index out of range`, `cannot convert float to int (nan or out of range)`), with exit status 1. Floats follow IEEE 754 except that dividing by 0.0 is `division by zero`, as in Python. Golden programs check them with `.err` files.
- Every stage must return an error, never panic, on bad input: `LexError` for bad literals, a `Diagnostic` from `Parser::parse`, `parser::MAX_DEPTH` for nesting, `Limits` in the interpreter, and `Err(String)` from codegen (`AssemblyGenerator::assemble` generates assembly without gcc).
- `src/codegen.rs`: `AssemblyGenerator` trait (`compile`/`assemble`/`scan`/`generate`/`emit`/`architecture`), `Architecture` (`X64`/`Arm64`: `host`, `FromStr` for `--target` names `x86_64`/`x64`/`aarch64`/`arm64`, `linker`, `generator`), and `link`, which writes `<output>.s` and runs the linker.
- `src/codegen/context.rs`: `Context`, the bookkeeping both backends share and hold as `ctx`: `check` (runs the checker) and `lower` (lowers to IR and notes the `Callee::Runtime` labels called, which `uses` answers), `new_label`, `intern_string`, `fail_label`, `print_routine`/`list_printers`, `needs_strings`/`needs_lists`/`needs_print`, plus `global_label`, `function_label`, and `immortal_string`.
- `src/codegen/ir.rs`: a small IR between the AST and assembly. A `Function` is blocks (in layout order) of `Inst`s over vregs, each ending in a `Terminator`; it is not SSA, so each stone local is one vreg for the whole function. `Display` prints a readable dump (`v1 = add v0, 1`, `br_lt v1, v0 -> b2, b3`), which tests compare and `STONE_DEBUG` prints. `Retain` and `Release` (`retain v1`, `release_str v1`) adjust a string's or list's reference count (`RcKind`), and `ListStore` can return the element it replaces (`v3 = list_store v0, 1, v2`).
- `src/codegen/ir/lower.rs`: `lower` turns a checked AST into a `Program` (every function, then `main`, plus the global names), resolving names like the checker (`checker::collect_assigned`). Evaluation is left to right, so runtime errors happen in the interpreter's order. `x = <expr>` writes `x`'s vreg directly, unless `x` is counted. `if`/`while` tests go through `Lowerer::cond`, so comparisons, `and`, `or`, and `not` become `CmpBranch`/`Branch` terminators instead of materialized bools. A `for` loop counts with hidden vregs that the body cannot assign, and copies a variable bound or list first. It also places every `Retain` and `Release` (see "Memory" below), which needs each variable's type, so it takes the checker's `symbols` as well as `types`.
- `src/codegen/ir/liveness.rs`: `analyze` computes live-in/live-out sets, then one interval per vreg (no holes). Each block gets a start position, then each instruction an even position where it reads and the odd one after where it writes. Intervals carry a spill weight (`10^loop_depth` per access) and whether they cross a call.
- `src/codegen/regalloc.rs`: target-independent `linear_scan` (Poletto-Sarkar, spilling the lighter interval) with `Hint`s for preferred registers (`hints` computes them from a function and its argument registers), and `parallel_moves`, which orders simultaneous moves and breaks cycles through a temporary.
- `src/codegen/x64.rs`: `X64Generator`, emitting GNU-as Intel syntax (`.intel_syntax noprefix`). `assemble` runs the checker first and lowers with its types, e.g. to pick a `print` routine per argument. Top-level statements always go in a synthesized `main`, globals live in `.bss` as `g.<name>`, and user functions are `fn.<name>`, so they cannot collide with libc. String literals are interned and emitted in `.data` with an immortal reference count (`builtins::immortal_string`). Runtime errors jump to a `fail_label(message)` stub that calls `stone.fail`.
- `src/codegen/x64/emit.rs`: instruction selection from allocated IR. Vregs that cross a call get callee-saved `rbx`/`r12`-`r15` (saved in the prologue only if used); others may also use `rsi`, `rdi`, `r8`-`r11`. `rax`, `rcx`, `rdx`, and `xmm0`-`xmm2` are never allocated and serve as scratch, for `idiv`, spilled operands, and wide immediates. `hints` asks for arguments to be computed in their argument registers, parameters to stay where they arrive, and copies and two-address results to share a register. The first six arguments go in registers via `parallel_moves`; arguments past the sixth are pushed, first deepest, and the callee reads them from `[rbp + 16 + ...]`. Each function counts itself in `stone.call_depth` against `MAX_CALL_DEPTH`, and each global has a `g.<name>.set` flag that `StoreGlobal` sets and that functions check before reading a global, since only top-level reads are checked statically. Floats travel as their bits in general registers and spill slots like every other value, and only move into `xmm` registers for SSE arithmetic, `ucomisd` comparisons, and conversions. Division checks for zero and `MIN / -1` before `idiv`, except that an immediate divisor other than 0 and -1 skips the checks, and a power of two becomes shifts (`divide_by_constant`). `%` shares those checks but gives 0 for a divisor of -1. `**` is an inline square-and-multiply loop (`power_loop`) that matches `stdlib::int_pow` and `stdlib::float_pow` operation for operation, and float `%` uses x87 `fprem`, so neither calls libc. List indexing is inline (`list_slot`): it counts negative indexes from the end, checks the result against the list header's length, and jumps to a `fail_label` when out of range. `Retain` is an inline `inc`, and `Release` an inline `dec` that calls `stone.free_str` or `stone.free_list` only when the count reaches 0. Those routines preserve every allocatable register, so neither instruction counts as a call for register allocation.
- `src/codegen/arm64.rs` and `src/codegen/arm64/emit.rs`: `Arm64Generator`, emitting GNU-as for AArch64 Linux from the same allocated IR, with the same labels, runtime failures, and `.bss` globals as x64. Arguments go in `x0`-`x7` and past the eighth at the bottom of the caller's frame (`[x29, #16 + 8k]` in the callee). Vregs that cross a call get `x19`-`x28`; others may also use `x0`-`x7` and `x12`-`x15`. `x8`-`x11`, `x16`, `x17`, and `d0`-`d2` are scratch, and `x18` is never used. `sp` stays 16-byte aligned at every instruction, so `push_frame`/`pop_frame` save registers in pairs and a frame reserves its spill slots and outgoing arguments once, addressing them from `sp`. Immediate forms of `add`/`sub`/`cmp` read register 31 as `sp`, so their first operand comes from `base`, never `xzr`. Behavior that differs from x86 is checked explicitly: `sdiv` never traps (zero and `MIN / -1` are tested first), `fcvtzs` saturates (the float is range-checked first), and float `%` calls `stone.fmod`, a wrapper around libm's `fmod` that preserves every allocatable register (hence `-lm`). Float comparisons use `fcmp` with `mi`/`ls`/`gt`/`ge`/`eq`/`ne`, which are false on nan except `ne`. `src/codegen/arm64/builtins.rs` ports every routine of `x64/builtins.rs` under the same label and contract; the free routines take the object in `x9`, libc's `stdin` is read through the GOT, and variadic `snprintf`/`dprintf` take a double in `d0`.
- Memory: compiled strings and lists are reference counted (the interpreter's `Rc` values need nothing more, and the checker's occurs check rules out cycles). Every object `p` has its count at `[p - 8]`, and `stone.alloc` (`builtins::memory_runtime`) allocates one with a count of 1. Strings stay null-terminated `char*`. A list is a 32-byte header `{len, cap, data, elem}`, where `elem` says whether its elements are counted (0 no, 1 strings, 2 lists) so `stone.free_list` can release them. `lower.rs` keeps counts exact: variables and list slots each own a reference, expressions are borrowed (variables, globals, literals) or owned temporaries (call results, list elements, which are retained when read) that whatever uses them releases or moves into storage, parameters are borrowed unless the function assigns them, `ret` releases locals and the lists of enclosing `for` loops, and the end of `main` releases every global. A row in `a[i][k]` is borrowed rather than retained when the index makes no calls (`Lowerer::list_operand`). `stone.live` counts allocated objects, and `stone.leak_check`, called at the end of `main`, exits with `error: N objects were never freed` when `STONE_LEAK_CHECK` is set.
- Builtins: `BUILTINS` in `src/stdlib.rs` lists function names shared by both backends (`print`, `range`, `int`, `float`, `str`, `input`, `eof`, `args`), and `BUILTIN_DOCS` documents each for hover and the LSP's builtins reference. `METHODS` (`len`, `append`, `strip`, `split`) and `METHOD_DOCS` do the same for builtin methods, which are called on a value (`xs.append(1)`, `s.len()`) and are not reserved names. `src/codegen/x64/builtins.rs` (and its port, `src/codegen/arm64/builtins.rs`) emits the hand-written runtime via `&mut dyn AssemblyGenerator`: `stone.print_*` routines (emitted if the program prints), the float runtime (`stone.format_float`, shared by `stone.print_float` and `str`'s `stone.str_float`, which calls libc's `snprintf` and `strtod` to match `stdlib::format_float`, which prints floats like Python's `repr`), and the string and list runtimes (emitted if the program uses those types). Other routines are emitted only if the lowered IR calls them (`Context::uses`, over `Callee::Runtime` labels): `io_runtime` (`input` via libc `getline` on `stdin`, `eof` via `getc`/`ungetc`), `args_runtime` (from `stone.argc`/`stone.argv`, which `main` saves on entry), `parse_runtime` (`int(str)` via `strtoll`, `float(str)` checking the grammar then `strtod`, both mirroring `stdlib::parse_int`/`parse_float` and failing with a message built at runtime through `stone.fail_quoted`), `conversion_runtime`, and `string_methods` (`strip`/`split`, mirroring `stdlib::strip`/`split_whitespace`/`split`). Whitespace is the ASCII set C's `isspace` uses (`stdlib::is_space`). Routines that call `malloc`/`realloc` realign the stack first, since generated code does not keep it aligned. `input` and `args` copy their text into counted strings. The `os` module's functions (`src/stdlib/os.rs`: `FUNCTIONS` and `DOCS` by linked name, such as `os.env`, plus the helpers the interpreter calls, the only `unsafe` code, for libc's `gethostname` and `sysconf`) are builtins too: `stdlib::is_builtin` accepts them, and each lowers to the runtime call `Context::OS_ROUTINES` names (`stone.os_env`, ...), emitted by `os_runtime` in both backends from the same libc calls. `os.exit` makes the interpreter return the error `interpreter::Exit`, which `driver::run_module`, `driver::repl`, and `main` turn into the exit status without printing anything, and compiled code calls libc's `exit`, skipping the leak check. Adding a builtin means updating `BUILTINS` and `BUILTIN_DOCS`, its type rule in `Inference::infer_builtin`, the interpreter's `Interpreter::call`, and its lowering in `Lowerer::call` (plus an IR instruction and its emission in both backends if it is not a runtime call), plus a program in `tests/programs/`. An `os` function follows the same steps with `os::FUNCTIONS`, `os::DOCS`, and `OS_ROUTINES`, plus a routine in each backend's `os_runtime`. A method follows the same steps with `METHODS`, `METHOD_DOCS`, `Inference::infer_method`, `Interpreter::call_method`, and `Lowerer::method`, and both backends evaluate the receiver before the arguments.

Language server (`lsp/`, crate `stone-lsp`, depends on `lsp-server`, `lsp-types`, `serde_json`):

- `src/lib.rs`: `run(connection)` does the initialize handshake (preferring UTF-8 positions, falling back to UTF-16), keeps open documents with full-text sync, and dispatches requests through `Server::answer`. On every open/change/close it reanalyzes every open document, reading files through `Workspace` (open documents' text over the disk), and publishes each one's diagnostics, the changed document first.
- `src/features.rs`: one pure function per request (`diagnostics`, `hover`, `definition`, `references`, `prepare_rename`, `rename`, `document_symbols`, `completion`) over a `Document`, which holds the text, the `stone::driver::analyze_linked` result of the whole program it belongs to (`Document::in_program`: the nearest `main.st` at or above it, or the file alone if that program does not use it), its `FileId`, the `SourceMap`, the program's imports, and a `LineIndex`. Spans in other files become locations through `Document::location`, and a library function's symbol is named `<module>.<name>`, which `Document::local_name` shortens. Builtins have no stone source, so `run` writes `stdlib::builtins_reference()` (comment-only, documenting each builtin from `stdlib::BUILTIN_DOCS`) to `<temp>/stone-lsp-<version>/builtins.st`, and `definition` of a builtin jumps to its line there (`Builtins`). Add a feature here with unit tests in `src/features/tests.rs`, then wire it into `Server::handle_request` and `capabilities`.
- `src/line_index.rs`: converts stone's 1-based char positions to LSP's 0-based UTF-16 or UTF-8 positions.
- `src/uri.rs`: converts between `file://` URIs and paths.
- Tests: unit tests for features and positions, `tests/server.rs` over an in-memory connection, and `tests/stdio.rs` against the real binary.
- `driver::analyze_linked` recovers from syntax errors statement by statement, in blocks too (`Parser::parse_recovering`, `parse_statements`), so features keep working around a typo, and it hides type errors until the syntax and `use` errors are fixed.

The logo is `docs/_static/logo.svg` (the S in Black Ops One, `#f1c232`), used by the docs and README. The VS Code extension can only package its own directory, so it keeps a copy as `editors/vscode/images/stone.svg` (the `.st` file icon) and a 256x256 render as `editors/vscode/icon.png` (the Marketplace icon, which must be a PNG).

`build/` is gitignored scratch output.

## Style

These apply to code, comments, docs, and commit messages.

- Never use em dashes.
- Never use emojis.
- Always use American English (e.g. "initialize", "color", "behavior").
- Doc comments (`///`, `//!`) are written in full sentences, and should include examples wherever practical:

  ```rust
  /// Rounds a frame size up to the 16-byte stack alignment required by the System V ABI.
  ///
  /// For example, `align16(20)` returns `32` and `align16(32)` returns `32`.
  fn align16(size: i32) -> i32 {
  ```

- Inline comments (`//`) start lowercase and are almost never full sentences, e.g. `// globals live in main's frame`, not `// Globals live in main's frame.`
